維護者 HTML 導航

以下不是普通連結清單，而是閱讀路線。先看左欄判斷何時用，避免在多個 HTML 之間迷路。若某頁保留在 PUBLIC，它就會進入 GitHub repo、GitHub Pages 或 npm tarball 的公開面；內容必須當作公開維護文件處理，不可放本機 evidence、私有路徑、草稿結論或未清理的內部痕跡。

  1. 先定檢查級別。打開 分層 QC，決定今次是快檢、外發前檢、全面檢，還是要直接跑七道驗收關口。
  2. 再定位產品流程。打開 APS 全流程地圖，找出改動影響安裝、共同基準、正式交接、check Drive、APS Live、修訂或收結哪一段。
  3. 涉及新手或 UAT 才看矩陣。打開 UX 矩陣，只用來設計觀察與驗收，不可原樣交給受測者。
  4. 最後回到公開頁。打開 公眾入口、教學中心 與相關教學頁，檢查新手是否按頁面提示就知道下一步。

公開承諾邊界

任何公開頁、README、CLI help 或技能提示都不可讓讀者誤以為尚未列入現有能力的事已可使用。

  • 可說：npx aps init 可建立初始設定，CLI 已支援最小收發、修訂、撤回、收結與健康檢查。
  • 必須同時說：每個真實跨機項目仍需各自驗證 Google Drive 同步；外部通知仍由人貼出，並應包含交接摘要與注意事項。
  • 必須標清：已發布主線是 Reliable Peer Handoff（Project Peers + Sent Status：同一項目可有多位協作對象，每次仍是一對一交接），確切版本以 npm @latest 為準；尚未發布的候選功能不可寫成公眾已支援。
  • 不可要求：核心設置不得要求額外雲端開發者專案、外部服務憑證或密鑰設定。
  • 不可說：完全自動、正式生產可用、免檢查、免人工確認、工具會自動向對方推送通知，或通知會自動觸發對方 AI。
Handoff Kit 整合邊界：APS 不改寫 AGENTS.md managed core。aps init 應只追加可移除的 APS managed block 到 dev\RULE_PACKS.md 與 dev\PROJECT_INDEX.md，並寫入 dev\rules\aps-bridge.md 與 .aps\config.json。日後 uninstall 應移除這些 APS managed block 與 APS 自有檔案，而不碰用戶原有 Handoff Kit 內容。

發佈前最低核對

發佈前不要只看文案是否順眼，要核對工具是否支撐了文案承諾。

  • 公開頁是否只承諾現有可用能力，未把目標體驗寫成已支援。
  • 新手教學是否不再要求閱讀或修改內部規格。
  • CLI 是否能用真實或 throw-away 共用 Drive 資料夾跑通 init（三問、只設自己一邊）、doctor、peers、peer invite（一次加入邀請碼；受邀者加入時建立本人身份）、peer add（已知對方 用戶名稱時才生成 provisional peer 與指定 starter pack，並非 init）、peer starter、publish --to <對象>（逐一指名收件）、inbox、consume、decline、close。
  • aps init 是否已註冊 Handoff Kit 可發現路徑：dev\RULE_PACKS.md 有 APS route，dev\PROJECT_INDEX.md 有 APS installed skill block，且 doctor 會檢查這兩項。
  • doctor 健康分兩層：本機核心（設定、橋接、上述兩項註冊、共用 Drive 資料夾 root、_hub 的 PROTOCOL/CHANGELOG、自己的 outbox/packets/ack、衝突檔掃描、身份結構掃描）決定退出碼；協作對象健康只供參考，永不影響退出碼。核對重點：未邀請對方的單邊新裝項目必須通過（exit 0），對方通道缺失不可令 doctor 失敗；lane / ack / peer card 的 agent、project、lane 錯配必須被揭示。
  • HTML 不可連結任何本地 .md 規格檔；需要提及時只用 plain path。
  • npm 版本、GitHub release、README、GitHub Pages 與本地 package.json 邊界一致。

最新 QC 覆蓋範圍

QC 觸發詞與分層規則以 dev\qc\triggers.md 為單一真源；QC 覆蓋狀態、缺口、阻塞與同步責任以維護者覆蓋登記表為單一真源。本頁只提示維護者：功能、流程或教學改動後，以下項目必須納入外發前檢與全面檢。

  • 新手頁的 SVG 宏觀流程圖與能力清單，須與 README、入口頁、CLI、skill spec、QC 真源一致。
  • 日常主路徑須是自然語言請 AI 操作；命令列只可作備用、排錯或維護者驗證。
  • 一語交接、發送前完整性預檢、摘要式通知、收件報告、本機對接檢查、補交需求、共識確認、回覆與收結，須在公開文檔、skill 與 QC 真源之間對齊。
  • 合作階段驗收矩陣須覆蓋初設、開局對齊、邀請加入、首次交接、日常推進、資料不足與解難、多人分工、修訂 / 撤回 / 收結、升級維護，以及 APS Live 產品標準驗收；每階段須同時核對 Terminal UX、HTML UX 與 packet 狀態。
  • APS 不自動發 Telegram / WhatsApp / Email，也不自動觸發對方 AI，不保證對方電腦即時同步；公開文檔與通知文字不得暗示相反能力。
  • 公眾入口與新手 HTML 只寫現有可用能力；未列入現有能力的產品路線名稱留在 Markdown 真源、維護者驗收頁與審核報告，不放入公眾頁面。
  • 若 HTML 參考卡與 dev\qc\triggers.md 或維護者覆蓋登記表不一致，先以對應真源為準，再立即同步 HTML。
