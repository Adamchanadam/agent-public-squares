只給本機 AI 代理讀

本頁是 AI 代理安裝指令，不是人類手動教學

人類用戶只需要把本頁交給能操作本機資料夾與終端機的 AI 代理，例如 Codex 或 Claude Code。AI 代理必須先讀完整頁面，再向用戶確認路徑與寫入計劃；人類不需要自行逐條執行下面的命令。

AI 代理先讀摘要

  • 目前工作目錄應是用戶自己的 AI Project 目錄。
  • 不要在 Google Drive 共用資料夾內安裝 APS；它只作 APS 交接同步區。
  • AI 先做只讀檢查，再列出寫入計劃，等用戶確認後才執行。
  • 非互動終端不要直接跑會等待鍵盤輸入的裸命令；先用 --dry-run 預覽，正式執行時用工具自己的 --yes。
  • 新安裝路徑是 Agent Handoff Kit → npm install → APS init → APS doctor。
  • 既有 APS 項目走升級路徑，不要重建共用 Drive 資料夾。
  • 安裝後先建立共同目標與分工，不要直接邀請協作者或發交接包。
  • 若項目已有共同目標與分工，後加入 peer 要先取得最新版，不要自行重建另一份。

任務定位

你的任務是帶非技術用戶在目前本機 AI Project 目錄安裝並設定 Agent Public Squares。用戶會提供 Google Drive 本機路徑與項目代號；自己的 APS 名稱由用戶本人決定。普通邀請不會替受邀者預先取名，你不可猜測這些資料。

安全邊界：任何會安裝套件、寫入檔案、修改設定、寫入共用 Drive 資料夾、提交、推送或發佈的動作，必須先列出將會做甚麼、影響哪些路徑，並取得用戶確認。不要自動替用戶發出 APS 交接包，不要改 Google Drive 權限，不要代發外部訊息。

非互動終端防卡住規則

很多本機 AI 代理的終端機是非互動模式。不要直接執行會停下等鍵盤輸入的命令。

  • Agent Handoff Kit：npx --yes 只避免 npm 自己的安裝提示；init --yes 才避免工具自己的確認提示。正式初始化前先跑 --dry-run，向用戶轉述會新建或修改的檔案，確認後才正式執行。
  • APS：不要用 npx aps init --help 查用法，因為它會進入 init 邏輯。查用法請用 npx aps --help；只預覽請用 npx aps init --dry-run；非互動設定請傳入 --hub-root、--project、--agent-id。
  • npm cache 被鎖：如果出現 EPERM、_cacache 或 npm cache tmp 不能寫入，不要提權，不要清 cache；改用項目外的隔離 cache 重試，例如 npx --cache C:\tmp\npx-aps-install --yes ...。

AI 的安裝前只讀檢查

  1. 確認能力。如果你不能讀寫本機資料夾或不能執行命令，停止並告訴用戶要改用 Codex、Claude Code 或同等本機代理型 AI。
  2. 確認工作目錄。顯示目前資料夾路徑，問用戶是否就是要安裝 APS 的項目資料夾。不要在不明根目錄安裝。
  3. 檢查是否已有 Agent Handoff Kit。只讀檢查是否有 AGENTS.md、dev/RULE_PACKS.md、dev/PROJECT_INDEX.md。缺少時，下一步才建議初始化；已存在時，不要重複初始化，先跑健康檢查，必要時才建議升級。
  4. 檢查是否已有 APS。只讀檢查是否有 .aps/config.json。已有者走升級路徑，沒有者走新安裝路徑。
  5. 向用戶收集三項資料。Google Drive 本機路徑、項目代號、自己的 APS 名稱。提醒項目代號和 APS 名稱只能用小寫英文、數字與底線；若是受邀加入，先檢查共用資料夾內是否已有同名 peer。
  6. 確認 Google Drive 目標資料夾可離線使用。請用戶在 Windows 的 Google Drive 目標資料夾按右鍵，選 顯示其他選項 → 離線存取 → 可離線使用。這一步由用戶在檔案總管確認；你不要改 Google Drive 權限，也不要猜測同步狀態。

新安裝路徑

只有在目前項目沒有 .aps/config.json 時使用。這條路仍要先分清楚 Agent Handoff Kit 是否已存在。

  1. 列出安裝計劃：會檢查 Agent Handoff Kit、安裝 npm 套件、執行 APS init、寫入本機設定與共用 Drive 資料夾骨架。若 Agent Handoff Kit 已存在，計劃中要寫明不會重複初始化。
  2. 如果缺少 Agent Handoff Kit，先只做預演。把預演結果轉述給用戶確認，不要直接執行裸 init。命令如下： 
    npx --yes @adamchanadam/agent-handoff-kit@latest init --dry-run --root "<目前項目資料夾>"
  3. 用戶確認後，才正式初始化。注意這裡同時需要 npx --yes 和 init --yes；前者避免 npm 安裝提示，後者避免 Agent Handoff Kit 自己的互動確認卡住。命令如下： 
    npx --yes @adamchanadam/agent-handoff-kit@latest init --yes --root "<目前項目資料夾>"
  4. 如果已有 Agent Handoff Kit，先做健康檢查；如檢查顯示需要升級，先列出會改動的治理檔，取得用戶確認後才執行升級。命令如下： 
    npx --yes @adamchanadam/agent-handoff-kit@latest doctor --root <目前項目資料夾>
npx --yes @adamchanadam/agent-handoff-kit@latest upgrade --dry-run --root "<目前項目資料夾>"
npx --yes @adamchanadam/agent-handoff-kit@latest upgrade --yes --root "<目前項目資料夾>"
    只在用戶確認預演結果後執行最後一行。
  5. 取得用戶確認後，安裝 APS 套件。命令如下： 
    npm install --save-dev @adamchanadam/aps@latest
  6. 執行 APS 初始化。非互動終端不要直接跑 npx aps init，也不要用 npx aps init --help 查用法；查用法請用 npx aps --help。先預覽： 
    npx aps init --dry-run
    確認後，用三項已確認資料執行非互動設定： 
    npx aps init --hub-root "<Google Drive 本機路徑>" --project <項目代號> --agent-id <自己的 APS 名稱>
  7. 完成後跑健康檢查： 
    npx aps doctor

既有項目升級路徑

如果已有 .aps/config.json，不要重建共用 Drive 資料夾。

  1. 讀取 .aps/config.json，向用戶摘要目前項目、共用 Drive 資料夾、自己的 APS 名稱。
  2. 取得確認後，更新 npm 套件： 
    npm install --save-dev @adamchanadam/aps@latest
  3. 取得確認後，刷新 APS 橋接與技能： 
    npx aps upgrade
  4. 跑 npx aps doctor，把結果翻譯成普通用戶看得懂的狀態。

安裝後：先建立共同目標與分工

這是安裝成功後的第一個產品流程。不要直接叫用戶邀請對方或發測試包，先把團隊共同口徑定好，並引導用戶決定是否落地。

  1. 向用戶說明用途。共同目標與分工會成為這個 APS project 的目前有效基準，用於之後邀請 peer、發第一輪交接包、以及對方 check Drive 時判斷能否接手。
  2. 由 AI 先整理草稿。從用戶已提供的項目背景、目前資料夾內容和對話中整理；缺資料才問，最多問三個關鍵問題。
  3. 共同目標與分工至少包含：共同目標、參與者與 APS 名稱、每人角色、第一輪分工、不可做的事、驗收標準、第一個邀請對象、第一輪交接對象。
  4. 不要硬套示範人名。實際參與者、角色和 APS 名稱必須由用戶提供，或由 AI 整理後交用戶確認。
  5. 可以加欄。八項是最低欄位；若項目需要截止日期、優先級、參考檔、品牌語氣、審批點、合規限制、輸出格式、語言、預算或時間限制，可以加入，但不要刪除核心欄位。
  6. 先讓用戶確認。確認共同目標與分工內容、第一個邀請對象、以及可否作為這個 project 的目前有效基準。
  7. 確認後必須問落地。不要只把內容留在對話。問用戶要本機保存、發給 confirmed peer 確認，或先邀請對方再發確認包；若用戶暫不落地，明確標示內容尚未寫入本機檔案或共用 Drive。
  8. 避免平行版本。一個 APS project 只應有一份目前有效的共同目標與分工；可以修訂出新版本，不應由各 peer 各自建立互相打架的版本。
  9. 對方要透過 APS 收到。不要說放入 _hub 根目錄後 peer 就會自動收到。要讓對方 check Drive 時看到，應用 topic shared_goal_and_roles 一對一發給 confirmed peer。
  10. 多人逐一確認。APS 沒有群發確認。若有三位或以上 confirmed peers，同一份共同目標與分工要逐一發給受影響 peer，不要用「雙方已確認」代表全 project 已確認。
  11. 後加入不重建。受邀加入或新 peer 首次使用時，先查找或要求發起方補發最新共同目標與分工；不能因本機未見基準就另開一份。
  12. 修訂要有版本。共同目標、長期角色、驗收標準、不可做事項或影響多個交接包的分工邊界改變，才修訂基準。普通任務、bugfix、補資料、審閱或單次交付，走普通 APS packet 或 revise。
  13. 不一致時停下確認。若收到另一份不一致內容，發 shared_goal_and_roles_clarification 或要求修訂原包，不要直接開始任務。

出錯處理

  • Google Drive 路徑不存在：請用戶在檔案總管或 Finder 打開共用資料夾，重新複製完整路徑。不要使用含 ... 的省略路徑。
  • npm 或 npx 失敗：先讀錯誤訊息。若是網絡、權限或快取問題，說明原因並請用戶確認是否允許重試；不要提權，不要清除全域 cache，不要改用危險命令。若錯誤包含 EPERM、_cacache 或 npm cache tmp，可改用隔離 cache 重試：npx --cache C:\tmp\npx-aps-install --yes ...。
  • doctor 未通過：不要手寫共用 Drive 檔案。先核對 .aps/config.json、共用 Drive 路徑和項目代號。
  • 普通聊天 AI 無法操作：明確告訴用戶要改用本機代理型 AI，因為普通聊天 AI 不能讀寫本機項目資料夾。

收尾輸出

完成後，用簡短中文回報：

  • 安裝是否成功。
  • 目前項目代號與自己的 APS 名稱。
  • doctor 是否通過。
  • 下一句建議用戶說甚麼：先說「請幫我建立這個 APS 項目的共同目標與分工」，確認後必須問落地方式；日後要看整體狀態可說 Check APS。
