分層 QC — 觸發詞彙

三級觸發詞彙將既有 QC 機制收口成 3 個入口。

本卡片：參考 觸發詞真源：dev/qc/triggers.md 覆蓋登記真源：OPS dev/qc/QC_COVERAGE_INDEX.md 建立：2026-05-21 S6

設計意圖

過往「全套 QC / 完整 QC / 跑驗收 / 整體 audit」此類含混詞容易令人類與 AI 對驗收範圍理解不一致。三級觸發詞彙鎖定三件事:每級的覆蓋範圍與時間、較高級別自動包含較低級別、含混詞觸發停手反問。

本卡片只屬日常閱讀與操作參考；觸發詞、級別定義與 QC 結果收口規則之單一真源為 dev/qc/triggers.md。完整流程覆蓋狀態、缺口、阻塞與同步責任之單一真源為 OPS dev/qc/QC_COVERAGE_INDEX.md。若本 HTML 與真源不一致，先以真源為準，並須將本卡片同步修正，不可讓讀者面長期漂移。

互聯查閱

本頁回答「叫 AI 跑哪一級 QC」；維護者頁回答「哪些文件與公開承諾要同步」；OPS 覆蓋熱圖回答「目前哪些流程有 QC、哪些仍有缺口」。

  • 維護者規格：真源地圖、發佈邊界、維護者核對入口。
  • APS 全流程地圖：按非技術用戶旅程檢查安裝、邀請、加入、共同基準、正式交接、收件、退回與收結是否真正可用。
  • APS 單機 UX Transcript 矩陣：逐一檢查非技術用戶語句、AI 第一屏、不可出現文字與單機通過條件。
  • 本機 OPS QC 覆蓋熱圖（只在本機 file:/// 開啟時自動連到 OPS 管理視圖）。

三級詳述

🟢 快檢

別名：跑快檢 / quick-check / qa-gate

時機：session 收工前；五區段執行完之後；commit / amend 之前。

覆蓋（4 項）：

  • kit doctor 報 status: passed
  • git status 同 handoff Workspace Identity 一致
  • 當次 session 所有 grep acceptance 全部命中
  • 有 script 改動：parse-check + DryRun against demo

驗收：四項全過。
失敗：修源重跑。

🟡 外發前檢

別名：跑外發前檢 / release-check / handover-verify

時機:物件離開本工作目錄之前(推送遠端 / 分享教學或維護者頁 / 傳一次加入邀請、指定 starter pack 或設置指引予協作夥伴)。

覆蓋：快檢全部 + 外發前檢區塊：

  • 跨工作目錄佔位符審核
  • README / 入口 / 教學 / 維護者 / skill / CLI 跨面交叉閱讀
  • HTML preview 視覺確認,包括 walkthrough SVG 與能力清單
  • PII / secrets sweep
  • 語氣與用語紀律掃描
  • 新安裝與既有項目升級路徑檢查
  • APS 跨機交接包、會話交接、品牌與版本分流檢查
  • Google Drive 已驗證主路徑與其他同步資料夾未驗證邊界檢查
  • User-facing 文檔內容與產品模型深審(改寫後全頁模型一致、多 peer 框架、圖文對齊 CLI)

驗收：快檢與本段列出的外發前檢區塊全過。
失敗：handover stop。

🔴 全面檢

別名：跑全面檢 / full-check / full-audit

時機：跨機往返測試 / 協定升版 / 引入新 AI 程式 / 治理工具重大升級之前。

覆蓋：外發前檢全部 + 人工 / 跨工作目錄項：

  • 跨工作目錄審核
  • 協定往返流程回歸測試
  • 啟動可發現性與橋接行為記錄
  • 五區段 / 自審 retrospective
  • 審核報告輸出
  • 規格與實際 runtime 行為落差審核

驗收：三條主線、主要流程、外發前檢區塊與人工 / 跨工作目錄項逐項收口,並提交審核報告。
失敗：逐條列阻擋項。

APS 全面檢三條主線

Agent Public Squares 的全面檢不只是多跑幾條命令,而是要證明公開說法、外發物可信度與協定實際行為三者一致。狀態須逐項標示為通過、失敗、受阻或接受風險。

主線要核對之事不通過時代表什麼
公開承諾一致性 README、入口頁、教學中心、第一次安裝與測試、本頁、維護者頁、CLI help、skill spec 對「目前可用」「使用邊界」「手動替代路徑」「npm publish 狀態」描述一致。 公開面可能把未發佈或未實作能力寫成已可用。
發佈前可信度 任何會離開本工作目錄的內容,包括 README、GitHub Pages、npm package、Bridge Pack、一次加入邀請、指定 starter pack、walkthrough、QC 卡片、維護者頁,皆須讓外部讀者理解並按當前狀態操作。 外人可能照文件操作卻撞上未核實、未發佈或不完整流程。
協定實際運行正確性 共用 Drive 資料夾協定、橋接規則包樣板、實際工作目錄、發件記錄、收件記錄、單寫通道、交接包版本、啟動時待處理計算、修訂 / 退回 / 撤回 / 收結行為、Handoff Kit APS route registration 與 project-index registration 須有實際操作記錄或對應工作目錄證據。 文檔說得通,但實際共享資料夾流程未必跑得通。

最新橫切保障

以下不是第四條主線,而是三條主線都必須覆蓋的防漏線。此段鏡像 dev/qc/triggers.md;若不一致,以該檔為準並同步本頁。

保障檢查重點
啟動可發現性 aps init 必須註冊 APS route 到 dev/RULE_PACKS.md,並在 dev/PROJECT_INDEX.md 記錄 APS local bridge / config;不可手改 AGENTS.md managed core。
新手主路徑 日常使用以自然語言請 AI 操作為主;命令列只可作備用、排錯或維護者驗證路徑。
宏觀理解與能力邊界 walkthrough 須先讓新手理解 APS 如何運作、已具備甚麼、使用邊界是甚麼。SVG 流程圖與能力清單不可誇大工具能力。
一語交接與雙向預檢 發送前須檢查共同目標、任務邊界、交叉點、請對方做的事、真源指標、接收方開工條件、風險與敏感資料;收件後也須產生收件報告,檢查是否足夠回應,並核對本機設定、文件資料、任務要求、真源指標、開工條件與版本狀態是否一致。
Project Peers 逐一交接隔離 涉及 APS 合作目錄層面的協作者 時,全面檢不可只跑二人往返。須至少驗證 A → B 單收件交接與 A → C 單收件交接各自 consume 或 decline；inbox --all / inbox --from 不可顯示不屬於自己的 packet；錯收件人 consume 必須被拒絕；status --packet-id 只查本機 agent 自己發出的 packet。新協作者邀請須用 peer invite 生成一次加入邀請碼,受邀者用戶名稱由本人決定;身份結構須由 doctor / Check APS 揭示 lane、ack、peer card 的 agent / project / lane 錯配。
補交與共識確認 交接不足時先發補交需求;理解不一致時先發共識確認包。未補齊或未達成共識前,不得把原交接收結。
通知與同步邊界 APS 不自動觸發對方 AI,也不保證對方電腦即時同步。AI 應生成可貼到 Telegram / WhatsApp / Email 的摘要式通知,包含重點摘要、注意事項與下一步。新手或狀態不明時先提示 Check APS;已確認基準且要讀具體交接時才提示 check Drive。對方看不到時先檢查 Drive 同步。
可行動狀態面 Check APS / check-aps 只可作 APS 整體狀態入口,顯示收件、發件、協作對象、下一步與風險。它只整理本機已同步資料中可追溯的行動線索,不是自動派工;不得改 packet / outbox / ack 狀態,不得取代 check Drive 收件入口,不得把一般「狀態」「check」「交接包」「收工」當成 APS 觸發,亦不得推斷對方已收到通知。若對方已 decline,發件方狀態面須顯示退回原因與 revise / withdraw / close 下一步。
新安裝與版本升級落地 若套件內 skill、CLI 或 setup wording 有變,須驗證新安裝與既有項目更新路徑。公開 HTML 只寫已公開可用的命令;其他測試路徑只記錄於 Markdown 真源與審核報告。
交接語義防混淆 「收工」應走會話交接;「交給 Jay / 對方 / 共用 Drive 資料夾」應走 APS 跨機交接包;只說「交接包」時必須先澄清,不得直接寫檔或寫共用 Drive 資料夾。
品牌與版本防混淆 APS CLI 版本與 Agent Handoff Kit 版本必須分開核實。APS skill 不得輸出 Agent Handoff Kit 啟動卡,也不得把 APS Hub doctor v... 當成 Agent Handoff Kit 版本。
長正文發包安全 正式交接、長正文、多行摘要、表格或含特殊符號的正文,應使用 --body-file 或等效安全輸入,不得把整段內容塞進一條多行 shell 引號命令。
雲端支援邊界 已驗證主路徑是 Google Drive,但不可固定磁碟機代號。其他同步資料夾若未完成驗證,不可在公開 HTML 寫成支援能力。
可靠二人協作防誇大 近期主線是可靠二人交接、發送前確認、收件總覽、補交 / 共識確認與 UAT。未列入現有能力的事,未有實作與 QC 證據前不可對外寫成已支援。核心設置不得要求額外雲端開發者專案、外部服務憑證或密鑰設定。

合作階段驗收矩陣

此矩陣把 APS 由初設到升級維護的合作旅程收口成階段級 QC。全面檢須同時核對 Terminal UX、HTML UX 與 packet 狀態；若加入 APS Live，Live 只可作即時釐清與協作加速層，不可取代 Drive packet / outbox / ack 正式帳本。

合作階段Terminal UXHTML UXpacket 狀態
初設階段 init 只設定本機 用戶名稱、project 與共用 Drive 路徑；已有 .aps/config.json 時走升級或切回既有項目，不覆寫。 新手頁與 AI 安裝頁須先提醒工作資料夾不可放在 APS 共用 Drive 內，並要求用戶確認寫入前置條件。 可建立本方 lane、ack、peer card；不得建立未加入者的 lane 或 ack。
開局對齊 Check APS 未見共同目標與分工時，須提示先建立或補發 shared_goal_and_roles，不要先發普通任務包。 Check APS terminal 狀態須顯示共同目標與分工狀態、下一步與逐人確認情況，不可把未確認基準寫成可開工。 shared_goal_and_roles 是 project 基準確認包；可修訂成新版本，不可平行存在兩套互相打架的基準。
邀請加入 peer invite 生成一次加入邀請碼；受邀者自行確認用戶名稱。peer add 只用於維護 / 兼容，且必須已約定用戶名稱。互邀時先選一個 APS 合作目錄作唯一合作空間，另一個邀請碼不用。 加入邀請頁須分清人類稱呼、APS 合作目錄名稱、用戶名稱、本機工作目錄、APS 交換區與 APS 合作目錄；加入後先 Check APS 核對基準。 一次加入邀請不得預建對方 lane / ack / peer card；重名、邀請碼已使用或 project 不一致必須阻擋；不得因收到邀請而建議改建或切換本機工作目錄；新建 APS 合作目錄須以合作項目或任務命名，不得用人名、電腦名、AI 名稱或發起人名稱。
首次交接 publish --to 必須單收件；正式交接用 --strict-handoff 檢查共同目標、任務、交叉點、請對方做的事、真源指標、接收方開工條件與風險。 公開頁、Check APS 與 APS Live 須保持「一對一交接、人工通知、收件方主動 check Drive」的邊界。 新 packet 寫入發件方 lane；版本、收件人、items 與 ssot_refs 須可追蹤。
日常推進 Check APS 看整體可行動狀態與共同基準；check Drive 讀具體收件。兩者不得混用。 Check APS terminal 狀態顯示待我處理、我交出去的事、等待對方、風險與同步資料；需要即時釐清時才引導 APS Live，正式寫入仍回到 terminal。 pending 計算須以 packet / outbox / ack 為準；context 只可作背景，不可覆蓋正式交接。
資料不足與解難 交接不足時提示補交需求或 decline；理解不一致時提示共識確認，不得硬開工。 Check APS 須顯示缺口、退回原因與發件方下一步，例如 revise、withdraw 或 close。 declined packet 不可仍列為 pending；未補齊或未達成共識前，不得收結原交接。
多人分工 同一 project 可有多位 peers，但每次 publish --to 仍須指定一位收件人；inbox --all 不可越權顯示別人的 packet。 Check APS 可顯示多位 peer 的確認狀態；每位用戶只能按自己身份看到的收件與發件狀態推進，不可照別人的狀態處理待辦。 A → B 與 A → C 須分別驗證 consume 或 decline；錯收件人 consume 必須被拒絕。
修訂、撤回與收結 revise 產生新版本；withdraw 只撤回未處理交接；close 只在回覆或完成後收結。 Check APS、status 與 check Drive 須顯示最新可行動版本與收結狀態，不可把舊版本當最新任務。 舊 packet 不可改寫；修訂、撤回、收結皆須保留 outbox 可追蹤記錄。
升級維護 既有項目走 upgrade，不得重跑 init 覆寫身份；升級後跑 doctor 與必要回歸。 AI 安裝頁與維護者頁須分清新安裝和既有項目升級；公開頁不可承諾未發布能力。 升級不得刪除或重建既有交接、ack、peer 或共同目標與分工。
APS Live 產品標準驗收 Check APS、check Drive 或 decline 只可在真實卡點提示「可開 APS Live 釐清」；驗收須先逐項走通 共同基準 → 已發出 → 對方查看 → 可開工判斷 → 處理 / 補資料 → 正式更新，再驗 Trystero 通訊。 APS Live 不可做成空白聊天室、訊息牆或泛用狀態牆。合格入口須先有六階段產品流程證據、可驗證通道、接收介面、狀態寫入邊界與確認閘；頁面只顯示階段名稱、同機截圖、local queue 或 console clean 都不可代替流程走通。 Live 訊息只可生成待確認草稿；正式狀態仍須回到 terminal，由用戶批准後經 publish、revise、decline、consume 或 close 落帳。

嵌套規矩

三級嚴格嵌套：

  • 跑外發前檢 必自動跑 快檢 4 項先
  • 跑全面檢 必自動跑 外發前檢(即同時包含快檢)

AI 不可在較高級別檢查被觸發後省略較低級別檢查。

典型用法

  • 🟢 快檢:commit 前 spot-check;五區段執行完之後之 baseline 驗證;改完 doc 試 anchor 不斷
  • 🟡 外發前檢:push remote 之前;傳一次加入邀請 / 指定 starter pack / 設置指引予協作夥伴之前;新教學頁或維護者頁分享予外人之前
  • 🔴 全面檢：跨機往返落地之前；協定升版之前；引入新 AI 程式之前；連續多輪工作後重置基線

更新覆蓋視圖

當開發繼續，OPS 覆蓋熱圖會因為新功能、新測試、新阻塞或已補齊缺口而漂移。要更新管理視圖，不要只改 HTML；先更新 OPS 覆蓋登記表，再同步相關 HTML。

下次可直接對 AI 說：

  • 「更新 QC 覆蓋視圖」— 讀 OPS dev/qc/QC_COVERAGE_INDEX.md，核對最新 QC 證據，更新 aps-qc-coverage-heatmap.html、本頁與維護者頁。
  • 「同步 QC 覆蓋登記表與 HTML」— 當你知道 QC 機制或覆蓋狀態已改，要求 AI 先改登記表，再同步熱圖和 PUBLIC 參考頁。
  • 「刷新 APS QC 熱圖」— 只想更新管理視覺時使用；AI 仍須先讀登記表，不能直接憑舊 HTML 改色或改進度條。

驗收要求：AI 應回報讀過哪些真源、哪些流程狀態有改、哪些頁面已同步，並用瀏覽器載入熱圖、本頁與維護者頁確認沒有錯誤。

如何呼叫

對 AI 說一句觸發詞即可：

  • 「跑快檢」— AI 跑 doctor + git status + grep set
  • 「跑外發前檢」— AI 跑快檢 + 9 項外發審核
  • 「跑全面檢」— AI 跑外發前檢 + 6 項人工 / 跨工作目錄審核;如涉及跨工作目錄,AI 列出需於對應工作目錄另開新對話處理的子任務
使用含混詞 = 觸發反問。如果用「做 QC / 跑驗收 / 整體 audit」此類詞,AI 會停手問「你指快檢 / 外發前檢 / 全面檢?」。這是防止範圍漂移的紀律,不是錯誤。
